## 三、各层职责一句话

| 目录 | 职责一句话 |
|---|---|
| `docs/` | 文档唯一真源（SSOT），不含任何运行时资产 |
| `dsh-plugin/` | 可运行的软件成果，唯一「碰了会中断运行」的目录 |
| `assets/` | 游戏运行时按 URL 引用的正式资产；路径是硬引用，子目录名别乱改 |
| `preview/` | 成果的**查看方式**，不是第二份成果库；永远不作运行时引用 |
| `workers/` | 资产生产管线：只生产，不保存正式成果；契约与可复现脚本入 Git，缓存/待验收/日志不入 |
| `tools/` | 项目级通用辅助 / 采集入口 / 维护工具，不参与生产流水线 |
| `memory-sync/` | 跨会话记忆同步状态，非项目事实源 |

## 五、Git 边界（什么入，什么不入）

- **入 Git**：docs/ 全文档、dsh-plugin/ 代码、tools/、workers/ 的 **契约 + 可复现生产/采集/校验脚本 + 必要输入资料**、preview/ 的 README 与代表性截图、assets/ 的结构与 manifest。
- **不入 Git**：`workers/缓存`、`workers/待验收`、`workers/运行日志`、`preview/全量高清预览与自动生成`、`assets/大图/视频/GLB 二进制`、`memory-sync/`。
- 原则：**契约和可复现生产的脚本属于源码，应被版本控制**；缓存与生成结果可以丢，契约不能丢。

---

*识别问题根：`workers/` 是最容易变成「什么都往里扔」的工作台——脚本、契约、输入、缓存、任务状态、日志现在应分层，别混同级。assets=正式成果本体，preview=正式成果的查看方式，八字要钉死。*
